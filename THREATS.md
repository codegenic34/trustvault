# THREATS.md

> Threat modeling, attack surfaces, security mitigations, and verification status for TrustVault.

## Threat Analysis & Mitigation Matrix

| Threat | Attack Vector / Scenario | What I did about it (Mitigation) | Status | Verification |
| :--- | :--- | :--- | :--- | :--- |
| **Insecure Direct Object Reference (IDOR)** | Attacker guesses, brute-forces, or uses leaked UUIDs of other users' documents. | All document operations query through central `authorize(user, action, docId)` with default deny. Non-existent IDs and unauthorized access both return identical `404 Not Found` responses to prevent ID enumeration. | **Mitigated** | Tested in test suite & API tests |
| **Inline Permission Bypass** | Developer introduces a new route or handler that forgets an access check. | Strict GEMINI.md rule: Zero inline authorization checks. Every route calls `authorize()`. No handler inspects raw document IDs directly. | **Mitigated** | Code architecture & audit checks |
| **Privilege Escalation (Admin Document Access)** | An administrator attempts to view or download sensitive client documents. | Admin role possesses **zero implicit document access**. Admins can only view audit logs and system telemetry; viewing a document requires an explicit `can_read` grant by the owner like any other user. | **Mitigated** | Verified in automated tests |
| **Privilege Escalation (Role Manipulation)** | A viewer or owner tries to assign themselves or another user the `admin` role. | `POST /api/admin/users/:id/role` strictly requires `admin` role and verifies CSRF. Non-admins receive `403 Forbidden` and the denied attempt is logged to the audit table. | **Mitigated** | Tested in test 8 of `npm test` |
| **Stale Session / Revocation Delay** | Access revoked or user disabled (`active = 0`), but user continues performing actions with old session. | Sessions and permissions are evaluated against the database on **every single request**. Revocation and user deactivation take effect instantaneously with zero grace period. | **Mitigated** | Verified in `auth.ts` middleware |
| **Password Change without Current Password** | Attacker with an open browser or stolen session attempts to reset the user's password. | `POST /api/change-password` requires the current password and validates it using `bcrypt.compare`. Failures are audited as `PASSWORD_CHANGE_FAILED`. | **Mitigated** | Tested in test 2 of `npm test` |
| **Session Fixation after Password Change** | Attacker retains the pre-change session ID after password is changed. | Session ID is immediately rotated to a new cryptographically random UUID in the database and issued via `Set-Cookie` on password change. | **Mitigated** | Tested in test 4 of `npm test` |
| **Stolen Session Surviving Password Change** | A previously stolen session cookie remains valid after the legitimate owner resets their password. | All other sessions for that user (`WHERE user_id = ? AND id != ?`) are atomically revoked in a single database transaction upon password change. | **Mitigated** | Tested in test 4 of `npm test` |
| **Brute-Forcing Authentication / Passwords** | Attacker launches credential stuffing or password brute force attacks. | Rate limited to 5 attempts per 15 minutes per authenticated user via `express-rate-limit`. IP-based rate limiting on login endpoint. Rate-limit breaches are audited. | **Mitigated** | Tested in auth middleware |
| **Malicious File Upload (Shells / Polyglots)** | Attacker uploads executable `.php`, `.js`, `.exe`, or polyglot files disguised as images/PDFs. | File extension allowlist (`pdf`, `png`, `jpg`, `jpeg`, `txt`, `docx`), strict 5 MB file size limit, and validation of file magic bytes prior to disk write. | **Mitigated** | Verified in `documents.ts` |
| **Direct File Path Traversal / Public Storage Exposure** | Attacker accesses raw files directly at `/storage/filename.txt` or uses `../` in requests. | Files stored outside web root (`storage/`) using random UUIDs. The `/storage` URL path is explicitly blocked (`404`). Streaming occurs only via authenticated download endpoint with sanitized headers. | **Mitigated** | Verified with direct endpoint tests |
| **Browser Script Execution via File Download** | Attacker uploads an HTML/SVG file disguised to execute scripts in the user's browser. | Downloads are served with `Content-Disposition: attachment; filename="..."`, `Content-Type: application/octet-stream`, and `X-Content-Type-Options: nosniff` so browsers never inline-execute. | **Mitigated** | Verified in `documents.ts` headers |
| **Audit Log Tampering / Repudiation** | Attacker or rogue admin attempts to update, delete, or wipe incriminating logs. | Audit log is append-only and hash-chained (each row stores `SHA-256(prev_hash + ...)`. SQLite database triggers (`BEFORE UPDATE`, `BEFORE DELETE`) raise hard aborts. | **Mitigated** | Verified in test 9 of `npm test` |
| **Cross-Site Request Forgery (CSRF)** | Malicious third-party website induces victim's browser to execute state-changing requests. | Every state-changing request (`POST`, `PATCH`, `DELETE`) requires a custom `X-CSRF-Token` header bound to the active database session. Cookies are marked `sameSite: 'strict'`. | **Mitigated** | Enforced across all mutating routes |
| **Cross-Site Scripting (XSS) & Clickjacking** | Injected malicious scripts or UI redressing attacks. | Hardened Helmet configuration with strict Content Security Policy (CSP), `frameAncestors: ["'none'"]`, `objectSrc: ["'none'"]`, and DOM text content rendering. | **Mitigated** | Configured in `server.ts` |
| **Reverse Proxy Cookie Interception** | Session cookies transmitted over unencrypted HTTP behind cloud reverse proxy (Render). | Configured `app.set('trust proxy', 1)` and set `secure: process.env.NODE_ENV === 'production'` for all session cookies so cookies require HTTPS in production. | **Mitigated** | Verified in `server.ts` and `auth.ts` |
